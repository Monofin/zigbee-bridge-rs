# Zigbee standards coverage

A protocol library covers the full assigned family for its stated revision, including optional forms. Record the specification, section, implemented operations and wire tests before marking a family complete. Track identifiers, payload codecs and device behaviour separately. Device support depends on role, cluster, revision and capability discovery.

## Device types and the runtime baseline

The [device-type inventory](tools/devices/README.md) joins all three pinned upstream listings to profile-scoped SDK templates wherever the source supplies an explicit profile and device ID. A template supplies possible roles. The member's Simple Descriptor supplies its actual servers and clients. The coordinator's `device/describe` returns these separately. Synthetic interview tests exercise each indexed template, including alternate templates for the same profile/type. Only HA and ZLL application profiles currently have a generic radio path.

The seven indexed profiles account for 59 Home Automation device IDs, 13 Light Link, 36 Building Automation, 22 Telecom Applications, 31 Health Care, 10 Smart Energy and 7 Green Power. Home Automation and Light Link use the runtime access described below. For the five specialist profiles the bridge can index and describe endpoints. Their commissioning, application traffic and native Home Assistant entities require profile-specific implementations and tests.

The [scalar attribute generator](tools/zcl/standard_attributes.py) uses the same hash-checked XML and attaches the wire type to each public server attribute. To check it, run `python3 tools/zcl/standard_attributes.py "$SDK_XML_DIR" --check`. A standard MQTT GET works for an unfamiliar model with a matching server. Unavailable optional attributes can return an error from the device. On/Off uses the standard control commands on confirmed actuators. Additional commands have dedicated implementations where the wire semantics and required capabilities have been reviewed. Client-side controls can produce a command event when the complete standard payload decodes. See the [MQTT contract](REFERENCE.md#interviewed-devices-and-standard-access).

### Generic application functions

The descriptor-only replay feeds the required roles of each pinned template through interview and MQTT discovery. It supplies no manufacturer overrides, optional attributes or recorded device responses. Counting distinct profile/device IDs with at least one functional entity or automation trigger, Home Automation goes from 20/59 to 47/59 and Light Link from 7/13 to 13/13. Link quality is excluded. In Home Automation, 31 IDs produce entities and 16 produce triggers. In Light Link, seven produce entities and six produce triggers. A type may have several templates. These counts measure whether any template for an ID exposes a function. Individual features and physical devices need their own checks. Reproduce these counts with `cargo test --locked -p zigbee-bridge-rs --lib all_indexed_type_templates_survive_interview_and_description -- --nocapture`.

The 12 HA IDs without a descriptor-only entity or trigger include configuration tools, gateways and range extenders whose mandatory clusters establish no user control. For a door lock, usable security and endpoint credentials are required. For a meter, scales and units matter. For an IAS Zone, the zone type determines the entity. These devices can gain functions during an actual interview.

The host registers four fixed application endpoints before network startup. Endpoint 1 preserves the original cluster roles. Additional client clusters use endpoints 2–4, with each Simple Descriptor fitting 64 bytes. New reporting bindings use the endpoint advertising the matching client cluster. Reports from older bindings to endpoint 1 remain accepted. EZSP 13 and 19 pseudo-terminals exercise the registrations and MQTT traffic. Acceptance on a physical network coprocessor remains open. Promote a profile to runtime support after an end-to-end commissioning and traffic test. Keep catalogue-only profiles identifiable in MQTT. |

The three locked upstream listings contain 123 rows with an explicit HA or Light Link Metering server, 118 with Electrical Measurement and 104 with Tuya MCU. Rows overlap and many definitions omit cluster fingerprints. These counts prioritize shared work. The [device inventory](tools/devices/README.md) and [function inventory](tools/devices/FUNCTIONS.md) retain the source evidence for each batch.

The [specialist profile review](tools/devices/SPECIALIST_PROFILES.md) traces 31 observed profile/device pairs outside the indexed templates to 174 endpoint declarations in the original selectors. They remain product-scoped evidence. Of 7,252 upstream rows, 1,204 supply a profile/device pair. The other 6,048 need live descriptors or independently sourced fingerprints to establish endpoint roles. Track implemented operations and their test evidence per family. A matching model name alone cannot establish operating support.

Three model-specific observations remain evidence-dependent. VALLHORN lux reports work, and the available descriptor lacks a pollable lux server. Two curtain variants confirm motor speed and have no confirmed direction readback. Only independent endpoint evidence or a physical observation should expand those contracts.

| Other general commands | R8 §§2.5.1–12, 2.5.15–17 | All 15 payloads encode and decode, including structured access, undivided writes, both reporting directions and compact success responses. | Behavioural rules and device interoperability. |
| Cluster-specific commands | R8 cluster tables listed below | 124 assigned commands in 18 clusters. Every assignment has an independent wire vector. | Remaining R8 clusters, including IAS ACE and Door Lock. |
| ZCL data types, statuses, clusters and profiles | R8 §2.6 and cluster chapters, plus profile specifications | Table 2-11 wire boundaries for every assigned data-type ID, including non-values, arrays, structures, sets and bags. | Core protocol | Zigbee Core, by revision | Pending. | NWK, APS, ZDO/ZDP, security and associated optional families require separate inventories and protocol tests. |
| Additional specifications | CSA specification catalogue | Pending. | Inventory applicable revisions and companion specifications, including commissioning, Green Power and Smart Energy. |

The reusable crate accepts an APS payload from any transport. It has no third-party dependencies. A parsed frame borrows its payload. Decoded record lists are owned and attribute values borrow the input. One command schema drives identification, payload dispatch and encoding. Shared record types define wire order once. Wire tests group commands by layout and keep independent expected bytes. Wire codecs describe field layouts. Device behaviour, transaction ownership, UART framing and MQTT mapping belong to their respective layers. Vendor extensions use manufacturer and cluster context.

References are the Alliance's *Zigbee Cluster Library Specification*, document 07-5123 revision 8, and the [CSA specification catalogue](https://csa-iot.org/developer-resource/specifications-download-request/). The catalogue lists Core revisions independently of ZCL. Each future Core family should identify the revision it implements.

The generator reads Silicon Labs' production Zigbee XML package from Gecko SDK v4.5.1. The package manifest names the inputs, including cluster extension files. The lock pins the commit and the SHA-256 of each input. The catalogue spans several specifications and cluster revisions. Generation includes the reviewed families above, removes six SDK-only commands from Basic, Identify and IAS Zone and excludes manufacturer-specific and sample definitions. Adding a family requires checking its assigned IDs in both directions and its field layouts against the relevant R8 tables. [Pinned SDK package](https://github.com/SiliconLabs/gecko_sdk/blob/8a2efd2cb191cb250fd4c1e655b16b8a80be1997/app/zcl/zcl-zap.json) · [Source lock](tools/zcl/source.lock.json)

The generator takes names, IDs, direction, field order and scalar types from the XML. Local rules cite the R8 clauses for differences. For example, OTA Query Next Image Response carries its image details only on success. For Level Control, R8 gives the with-On/Off variants the same payloads as their counterparts, including the options bytes. A legacy lighting frame can omit those bytes. The decoder supplies the specified zero defaults and the encoder emits both fields. [Generator](tools/zcl/generate.py) · [Wire tests](crates/zigbee-zcl/tests/cluster.rs)

Scene extension field sets retain the cluster ID and its length-delimited octets, including unknown cluster IDs and trailing attributes. Interpretation of the individual cluster attributes is pending. The membership codecs derive the element count from the list. Recall Scene preserves an omitted transition time separately from an explicit zero or 0xffff.

For Thermostat, R8 §§6.3.2.3.2 and 6.3.2.4.1 give Set Weekly Schedule and its readback the same wire layout. The SDK labels the transitions as an array of octets. Both codecs expose signed heat and cool setpoints selected by a common mode, and derive the per-command count from at most ten transitions. Attribute discovery, device schedule capacity and applying multi-command schedules belong to the device layer. Figure 6-14 labels relay status as map8 but allocates two octets. The codec follows the two-octet layout and the SDK bitmap16 definition. For IAS Zone, Table 8-11 assigns two server command IDs. The two additional mode responses in the SDK are excluded.

The public Alliance-origin Dotdot XML describes its original R7 conversion. The ZAP project's separate Silicon Labs snapshot explicitly includes test data. Use the Alliance R8 document for revision and wire semantics. The generated metadata retains the upstream copyright and Apache-2.0 notice. Run `python3 tools/zcl/generate.py --check` to fetch the pinned inputs and verify the checked-in result. Use `--source /path/to/gecko_sdk/app/zcl` for offline regeneration or checking. Omit `--check` to write the module. Cargo builds use the checked-in Rust. The library dispatches on APS cluster, ZCL direction and command ID. `Command::decode` checks the entire payload. `decode_prefix` returns any trailing bytes for forward-compatible callers. The original `Frame` preserves the exact received bytes, including unknown commands and legacy encodings.
