# Rehearsing a Zigbee2MQTT migration

The import works offline, using a copy of the Zigbee2MQTT data directory. It stages host-side identity and interview records for a bridge using the same coordinator and commissioned network. A stage can succeed while the replacement still lacks device functions or Home Assistant entities.

## Stage a fresh directory

1. Take a coherent snapshot of `configuration.yaml`, its referenced device/group files and `database.db`. Use a private directory outside Git. A rehearsal can use a projected copy containing the required fields and a separate record of what was omitted.
2. Run the inspector. Review rejected and held-back records, missing configured devices and unsupported settings. It prints counts only.
3. Stage the same input in a new directory outside the snapshot, on the filesystem that will hold the candidate. The importer publishes that directory with an exclusive rename after reopening its store and validating its membership records.

```sh
cargo run --locked --bin z2m_migrate -- inspect SOURCE
cargo run --locked --bin z2m_migrate -- stage SOURCE NEW_STATE
```

`devices.json` carries stable IEEE addresses and configured friendly names. `members/*.member` carries observations derived from persisted endpoint descriptors and selected Basic and Color Control identity/capability attributes. Each target observation names the Zigbee2MQTT database as its source. The stored short address belongs to that historical observation. The active registry starts with unknown short addresses so the adapter resolves current routes when required. An omitted descriptor version is recorded as unknown. Imported entries use zero for an unknown historical observation time. Repeating the stage from identical data produces byte-identical membership files. Device credentials and cached light states are excluded. See the [address resolution audit](ADDRESS-RESOLUTION.md) for cold-table behavior and the remaining cutover risks.

A TS0210 vibration sensor retains its configured `vibration_timeout` in seconds. Zero disables the automatic clear. An absent setting uses the device handler’s 90-second default.

A staged coordinator restores the `advanced.last_seen` format and publishes host reception times for current members. Startup discovery uses declared standard measurement servers, reviewed optional device attributes and supported battery reporting from the copied record. A saved reporting configuration establishes capability only. The sensor receives its first value from a subsequent radio report or a successful read.

Pending, failed, and incomplete device interviews, disabled devices, and configuration entries without a device record are counted separately. Unsupported per-device options, Home Assistant overrides, groups, Green Power records, schedules, and cached broker state require review. A selected copy can reveal only the options it preserved.

`reconciliation/expectations.json` is a private, offline inventory for subsequent read-only comparison. Each source IEEE and endpoint records its cached binding destinations (group or endpoint), clusters, configured report attributes, direction, intervals, change and manufacturer code where known. Herdsman's configured-report cache represents reported attributes, ZCL reporting direction 0. Counts include any coordinator records with endpoint entries. Unrecognized rows are counted and held back. The importer emits no Zigbee commands. Replacing the host while retaining the same coordinator normally preserves device-side binding tables and reporting settings. The old host cache can have diverged from actual device configuration. After a separately approved radio handover, read binding tables and reporting configuration, account for sleeping devices, and review differences before changing anything. [Herdsman endpoint persistence](https://github.com/Koenkk/zigbee-herdsman/blob/master/src/controller/model/endpoint.ts)

To rehearse rollback without opening a coordinator, mount the snapshot read-only, disable network access and expose only the destination directory to the staging process. Hash the source files, stage twice into different fresh directories, and compare file names and contents recursively. Attempt to stage into both an empty existing directory and a populated candidate, and check that both are intact after refusal. Move the candidate aside, rerun the inspector on the original snapshot, and compare its output and the source hashes. This verifies the host-side reversal. Radio backup, service handover and Home Assistant continuity need separate evidence.

## Compare retained Home Assistant discovery

Take an owner-scoped snapshot of the *old* retained discovery topics. Preserve each discovery topic, unique ID, device identifiers, platform/component, state and command topics (including property-specific variants), relative topic base, and trigger type/subtype/topic for device automations. Keep the same MQTT base and discovery prefix on both sides of the comparison. Include the coordinator IEEE when rendering the candidate if the existing bridge includes coordinator-scoped identities.

```sh
cargo run --example discovery_snapshot -- NEW_STATE MQTT_BASE DISCOVERY_PREFIX --coordinator-ieee COORDINATOR_IEEE --jsonl > candidate.jsonl
python3 tools/devices/discovery_parity.py old.jsonl candidate.jsonl --prefix DISCOVERY_PREFIX --details private-differences.json --require-match
```

Pass the same `--light-index PATH` to the example that the bridge will use. Keep snapshots and the generated details private. The comparator accepts JSONL and JSON arrays of `{"topic":".../config","payload":{...}}`, resolves Home Assistant abbreviations and relative topics, and uses the last retained record for each topic. An empty-string payload clears the topic. Supply a complete, scoped capture of current retained messages. The tool has no broker connection and cannot detect missing capture fields.

The aggregate counts report stable, missing, new and changed identities, changed discovery or command/state routes, reused discovery slots and conflicting IDs. Entity unique IDs are scoped to platform. Device automations are matched by device identifiers, automation type, type and subtype, and their trigger topics are compared. The comparison includes every declared metadata field, including unknown fields. The optional private details file identifies changed field paths without printing arbitrary metadata values. Review changes to statistics in both directions. Adding a state class can start long-term statistics that the original discovery will stop on rollback. An existing statistics ID can also change meaning if the new class or unit changes. The strict gate exits with status 1 for any difference, conflict, unidentifiable record or two empty inputs. Status 2 indicates an input/output error. Verify the behaviour of MQTT payload templates, device actions, configuration overrides, retained state, HA's registry and actual state/command round trips independently. Names, areas, disabled entities and automation references may depend on HA’s existing registries. [Home Assistant MQTT discovery](https://www.home-assistant.io/integrations/mqtt/#mqtt-discovery) · [HA discovery abbreviations](https://github.com/home-assistant/core/blob/2026.11.3/homeassistant/components/mqtt/abbreviations.py)

Run `python tools/devices/validate_ha_discovery.py < candidate.jsonl` in a disposable environment containing the target HA Core version. The tool applies HA's MQTT platform schemas and compiles templates, then checks each sensor's state class against HA's device class rules. This checks the rendered inventory offline. It does not exercise a physical device or modify a recorder database.

Keep `discovery-topics.json` with the coordinator state directory. It records managed interview-derived Home Assistant topics by broker, bridge base, discovery prefix and IEEE address. When a later interview removes a capability or changes its Home Assistant domain, the bridge clears the superseded retained config. At startup it rechecks outstanding topics against the saved member and waits for broker acknowledgement before retiring ownership.

### Exercise retained-message rollback

On a disposable loopback Mosquitto instance, set `ZIGBEE_OLD_DISCOVERY` and `ZIGBEE_TRIAL_DISCOVERY` to the two JSONL snapshots and run `cargo test --test discovery_rollback -- --ignored --nocapture`. The test uses a fresh topic prefix. It subscribes as a new client to capture the baseline, applies the candidate declarations, restores the saved bytes on overlapping topics, clears candidate-only topics, then checks every retained message with another subscriber. An unrelated retained publication must also survive. Projected inputs exercise this sequence, while production recovery requires the original full payloads and registry backup.

## Radio and rollback gates

Run `cargo run --locked --bin z2m_migrate -- check-adapter BRIDGE_INFO_JSON` on a private, read-only snapshot of the original service’s retained `bridge/info` payload. The check only needs `coordinator.type` and `coordinator.meta.ezsp`, so a projection of those two fields suffices. An unsupported protocol exits unsuccessfully before the replacement acquires any serial port. A match clears only the host protocol version gate.

The importer leaves the radio, original directory, MQTT broker, and Home Assistant untouched. Backup *presence* in its report only checks the filename. Coordinator NVRAM, live security counters, backup integrity and restore compatibility cannot be verified offline by this tool. An absent backup is expected in a redacted rehearsal. Keep the original host state and a verified, adapter-compatible recovery backup private before any production handover.

Hold a handover while discovery differences, required device functions, copied overrides or expectations are unresolved. Rehearse with a separate broker. Preserve the original retained messages and HA registry. Confirm that the candidate supports the deployed adapter firmware and network resume before attaching it. A cutover needs exclusive adapter ownership, a closed joining window, and verification of the expected PAN, extended PAN, channel and coordinator IEEE.

Before a production candidate has touched anything, rollback is simply to leave the existing service running and set aside the staged directory. After an approved same-network trial, stop and drain the candidate, verify the serial port is released, and restart the original Zigbee2MQTT service with its unchanged state and the same coordinator. Confirm the network identity, fresh device reports, scoped discovery and a known-safe read. If the candidate published production discovery, restore specifically recorded topics and review candidate-only topics before clearing them. If radio state changed, use the verified adapter-specific recovery procedure with the owner; an older backup can have stale security counters. Factory reset or re-pairing is unnecessary for a host-only rollback.

## EZSP 19 adapter gate

**The bridge negotiates EZSP 13 and 19.** A second VERSION exchange confirms a switch to 19 before runtime traffic. A matching extended frame header and successful VERSION exchange do not establish compatibility for startup, address resolution or message delivery. The following audit covers the commands and callbacks used by the current coordinator, interview and managed MQTT paths. Silicon Labs' generated host implementations are pinned to Gecko SDK 7.4's protocol `0x0d` and Simplicity SDK 2026.6.2's protocol `0x13` (decimal 19). **Verification gate.** The in-tree v19 codec has passed vendor-derived wire vectors for failed address lookup, status values above 255, tags with equal low bytes, source/LQI preservation and truncated responses. The existing v13 PTY tests exercise reset between ASH ACK and EZSP completion. The existing v13 dongle can exercise v13 regressions on an isolated network. An independent version probe and a read of the stored coordinator node identity have succeeded on isolated EZSP 19 hardware. A production handover still requires verification of the deployed firmware’s network resume, trust-centre policy readbacks, and a correlated end-to-end exchange alongside the migration checks above.


### Isolated hardware evidence

The bench Dongle-M resumed its channel-20 bench network after an application-only MG24 upgrade from EmberZNet 7.4.5 to 9.1.1. At 115200 baud, with host flow control disabled, the Rust host confirmed EZSP 19, inspected the saved node token, resumed the coordinator, and completed MQTT health and timed/explicit permit-join operations. Independently read backups agreed on coordinator IEEE, PAN, extended PAN, channel and network key. The network key frame counter did not regress. This clears the v19 protocol gate for that bench. A migration to another adapter and firmware combination still requires the HA, device and rollback checks above.

For recovery, keep the original application image, Open Coordinator Backup and raw token export private. Save an up-to-date backup before any downgrade. Firmware upgrades can change the token table. Restoring an older counter or replaying old tokens across revisions can interrupt secured traffic.

### Device availability

The importer carries the `availability` section and device overrides into `availability.json`, together with each admitted member’s power classification and last recorded sighting. Missing timestamps start offline. Availability is opt-in, as in Zigbee2MQTT. Include this policy and the runtime `availability-seen.json` checkpoint when copying the state directory. The radio session checkpoints changes every minute and on orderly shutdown. A process crash can lose up to one checkpoint interval of sightings.

Enabled devices publish retained QoS 1 JSON on `<base>/<friendly_name>/availability`. Home Assistant requires both this topic and `<base>/bridge/state` to be online. Endpoints share the physical device’s topic. Managed startup publishes bridge-offline while it restores all current device states. It publishes bridge-online after the broker acknowledges those states. Sleeping devices can become unavailable when their reporting timeout expires. Mains devices receive a Basic `zclVersion` read after silence, with a second attempt for a previously online device. A received message confirms presence. Each read resolves the destination from its IEEE address, and the radio session allows one probe at a time.

The bridge records the availability names it owns in `availability-topics.json`, scoped to the configured MQTT host, port and base topic. Keep that file with the state directory. Startup clears a retired name only when it previously belonged to this bridge and no current monitored member uses it. The ledger drops the name after the broker acknowledges the retained deletion. A radio leave publishes offline while the member remains enrolled.

## IAS assignments across a handover

Keep `ias-zones.redb` alongside the member records in the bridge state backup. For a filesystem copy, stop and drain the bridge first, copy the complete state directory, and restore it with the same coordinator identity and network. The IAS store checks its coordinator IEEE address at startup. A live or cross-adapter backup of the complete coordinator needs the separate recovery rehearsal.

On a staged Zigbee2MQTT import, the first managed session reads existing IAS servers to learn their panel and zone IDs. It preserves a valid ID reported for this panel. A sensor that has not answered can delay *new ID allocation* while other enrolled devices continue reporting. Inspect the member’s enrollment state with `device/describe`. Before an operational handover, verify the existing zones and observe an actual opening and restore at a contact. Keep the original coordinator state for rollback. Enrolling a previously unclaimed sensor changes the sensor itself.


Keep `admin-transactions.redb` and its `admin-transactions.required` marker in the stopped bridge backup. The marker makes a missing or empty journal a startup error. Restore it with the same device records, coordinator and MQTT base topic so retried binding, joining and OTA requests see their recorded outcomes. Up to 8,192 transactions share the journal. Completed records expire after seven days. Interrupted reservations persist. A full journal rejects fresh tagged changes before sending radio work. This version has no operator command to clear an indeterminate reservation.

Restoring an older backup only recovers transactions recorded by the time of that snapshot. Reconcile requests accepted since the backup against device and network state before resuming publishers that can retry them.

Keep `mqtt-state.redb` and its `mqtt-state.required` marker in the same stopped-state backup as the member records. It stores the latest checkpointed readings by IEEE and endpoint and broker-scoped retained deletion obligations. Ordinary readings are checkpointed every 30 seconds and at orderly shutdown. An abrupt stop restores the last successful checkpoint. Retained deletion obligations commit immediately. Restore it with the matching network. The managed publisher rebuilds current state on reconnect. Gesture events are transient.

During trial recovery the exclusive discovery writer has 15 seconds before it is stopped and joined. Recovery then starts the original container and checks its health. An outstanding discovery mismatch keeps the handover marker. Subsequent recovery attempts with the original owner active only read the broker. Inspect unresolved differences before scheduling a new exclusive repair.
